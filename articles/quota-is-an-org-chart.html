Quota Is an Org Chart

Your provider meters the organisation. So the first team to ship a backfill sets everyone else's error rate.

2026-10-075 min readplatform-team · rate-limits · org-design · ai-infrastructure
Common Assumption

429 errors mean we need a higher tier from the provider. Rate limits are the vendor's problem to raise.

Actual Inflection

A 1.5M-token-per-minute backfill on a 2M limit throttles ~29% of 1.3M TPM interactive traffic at peak. The fix is allocation — sub-limits, lanes and caching — not a bigger tier.

Before scale

Every major model API meters usage at a level above the team that builds the feature. OpenAI defines rate limits at the organisation and project level — requests and tokens per minute and per day — and some model families share a single limit, so calls to any model in the group draw from the same budget.[1] Anthropic measures requests, input tokens and output tokens per minute at the organisation level, with optional workspace-level sub-limits set by administrators, and refills capacity continuously with a token-bucket algorithm rather than resetting each minute.[2]

Those are sensible designs for a provider. Inside a company they create a commons. The support assistant, the coding agent, the nightly document-classification job and the data-science team's evaluation run all draw from one bucket. When the bucket runs dry, the provider returns 429s to whichever request arrives next — and it has no idea which of your teams matters more.

At pilot scale this never comes up. At production scale it decides who has an incident on Tuesday morning.

Perspective shift — beat 1
“We hit the provider's rate limit”→“One of our teams spent everyone's rate limit”

A 429 looks like an external failure, so it gets an external fix: ask the account team for a higher tier. OpenAI raises tiers automatically as spend grows, and enterprise contracts raise them further.[1][4] But a bigger bucket does not change who drinks from it. If the backfill job is written to use whatever is available — and most are, because that is the fastest way to finish — it will use the new headroom too. The cause was never the size of the limit. It was that nobody decided who gets it.

A Shared Limit Is a Shared Budget

Treat the organisation's rate limit as what it is: a budget, denominated in tokens per minute, shared by every AI workload in the company. Budgets need allocation rules, owners and enforcement. Most AI orgs have none of the three for rate limits. They have a single API key, or a handful of projects created ad hoc, and a hope that peaks don't coincide.

Peaks do coincide, because the workloads fighting over the bucket follow the same clock. Interactive traffic peaks in business hours. Batch jobs get scheduled “overnight” in a time zone that is somebody else's business hours. Evaluation sweeps run when a release is close — exactly when the product is being demoed. The collision is structural, not bad luck.

That is why quota is an org chart. Whoever controls the allocation decides which team's users see errors when demand exceeds supply. If nobody controls it, the allocation is made by whichever job is greediest — usually the one with no users waiting on it.

Anatomy of a Tuesday Morning

Take one organisation-wide input limit of 2 million tokens per minute. Interactive traffic — support assistant, in-product copilot, agent sessions — peaks at 1.3 million. A data team launches a document backfill sized to finish fast: 1.5 million tokens per minute. With no prioritisation, the provider throttles whichever requests arrive when the bucket is empty, so interactive traffic loses roughly in proportion to its share of demand.

After scale
Perspective shift — beat 2
“Each team manages its own API usage”→“Each team's usage is every team's latency”

Distributed ownership of a shared limit fails the same way any unpriced commons does. No team is rewarded for leaving headroom, and every team is rewarded for finishing faster. Retries make it worse: throttled clients back off and retry, adding demand exactly when the bucket is empty, so a short overload can stretch into a long one. The second-order cost is trust. After two or three incidents, product teams ask for their own provider accounts — which removes the contention but recreates the duplicated-infrastructure problem a platform team exists to prevent.

The Tools Already Exist

Providers and clouds already ship the mechanisms for allocation. What's usually missing is the decision to use them and someone who owns the policy.

Workspace and project sub-limits turn one org-wide bucket into per-team budgets.[1][2] Spillover on Azure sends requests that overflow a provisioned deployment — the ones that would get a 429 — to a standard pay-as-you-go deployment instead of failing them, which gives interactive traffic a defined overflow path.[3] Caching raises the effective ceiling: because cached reads don't count towards Anthropic's input limit on most models, an 80% hit rate turns a 2M-token limit into roughly 10M tokens of total input per minute.[2]

The common thread: each mechanism encodes a priority. Somebody has to decide that the support assistant outranks the backfill and the backfill outranks the experiment. That decision is organisational, and it is the actual work.

Your Counterargument

“A central gateway with quotas is a bottleneck in waiting. We'll recreate the platform-team queue we just escaped. Teams should own their keys and their limits; if they hit 429s, they can ask for more.”

That's the right fear and the wrong conclusion. A gateway that requires approval for every new use case is a bottleneck. A gateway that enforces published, self-serve budgets is plumbing. The distinction is the same one as for platform teams generally: an internal vendor provides capacity with clear rules; a gatekeeper rations it through tickets. Separate keys per team also don't create separate capacity — every project still sits under the organisation's limit and tier,[1] so separate keys just hide the contention until it surfaces as an incident.

Start with the lightest version: per-team sub-limits in the provider console and a rule that batch work runs in its own capped project. Build a gateway when you need priority lanes.

What to Do

  1. Split the org limit into published team budgets.

    Use project or workspace sub-limits so each team's ceiling is explicit and the sum leaves headroom for interactive peaks.[1][2] Publish the table where every team can see it.

    This week: export last month's peak tokens-per-minute by key or project.

  2. Give batch work its own capped lane.

    Backfills, evaluation sweeps and re-indexing run in a separate project with a hard cap below L − I. Use asynchronous batch interfaces where your provider offers them.

    This week: move the largest scheduled job into its own project with a cap.

  3. Rank workloads, and write the ranking down.

    Decide in advance which traffic gets throttled first when the limit is hit. Encode it as sub-limits, spillover[3] or gateway priorities — never as whoever retries fastest.

    This week: draft a three-tier priority list and get engineering leads to agree to it.

  4. Count caching as capacity.

    Report effective throughput — total input ÷ uncached input — alongside the raw limit. A falling hit rate is a capacity incident in waiting.[2]

    This week: add cache-adjusted headroom to the capacity dashboard.

In the next 24 hours

Find out how many API keys and projects your company uses against each AI provider, and who can launch a job that uses all of the organisation's rate limit. If the answer is “anyone”, put a cap on the next batch job before it runs.
