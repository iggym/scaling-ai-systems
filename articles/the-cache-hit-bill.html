The Cache Hit Bill

You negotiated the token price. The number that actually sets your bill is a cache hit rate nobody owns.

2026-10-074 min readcost-economics · inference-economics · prompt-caching · platform-team
Common Assumption

Input cost is price × tokens. To cut the bill, negotiate a discount or move to a cheaper model.

Actual Inflection

With prefix caching, input cost swings nearly 4× between a 40% and a 90% hit rate on the same model and price. Below a ~22% hit rate, cache writes cost more than they save.

Before scale

Prompt caching is the largest price cut most AI teams never fully collect. On Anthropic's API, reading a cached prefix costs 0.1× the base input price — a 90% discount — while writing one costs 1.25× for the default five-minute lifetime, or 2× for a one-hour cache.[1] OpenAI applies caching automatically to prompts of 1,024 tokens or more, matching on exact prefixes, and bills cached tokens at a discount.[3][4]

There is a second benefit that matters more at scale than the price. On Anthropic's API, for most current models, cached input tokens do not count towards the input-tokens-per-minute rate limit.[2] A team at an 80% hit rate can push about five times more total input through the same limit as a team with no caching.

So the bill and the rate-limit headroom both depend on one number: the share of input tokens served from cache. In most orgs, nobody is responsible for that number, and the architecture slowly works against it.

Perspective shift — beat 1
“Caching is an optimisation we turned on”→“Caching is a contract every prompt editor must keep”

Cache hits require the start of the prompt to be byte-for-byte identical to a recent request.[3][4] That makes the hit rate fragile in a way a feature flag is not. Put a timestamp at the top of a system prompt, insert the user's name before the shared instructions, reorder tool definitions, or run three prompt variants at once, and the shared prefix that made caching pay disappears. Nothing breaks. The bill simply goes up, and no alert fires.

The Prefix Is Shared Infrastructure

At pilot scale one engineer owns the prompt, and caching works because one person keeps the prefix stable. At scale the system prompt is edited by product, safety, legal, platform and growth teams — each adding a paragraph, a policy line or an experiment. Each edit is reasonable. Together they turn the prefix into a moving target.

The economics are unforgiving because cache misses are not free. With a five-minute cache on Anthropic's pricing, every miss pays a 25% write premium on top of the base price.[1] If each request either reads (0.1×) or misses and rewrites (1.25×), the effective input multiplier at hit rate h is 0.1h + 1.25(1 − h). That equals 1.0 — the no-cache price — at h ≈ 21.7%. Below that, caching makes the bill worse. Above it, every point of hit rate is money.

That turns the prefix into shared infrastructure, like a database schema: something many teams depend on and nobody should change casually. Most orgs treat it as a text file anyone can edit.

Below a 22% hit rate, caching costs more than it saves. Above it, every point of hit rate is money.

After scale
Perspective shift — beat 2
“We'll tune caching once costs matter”→“Prompt governance is cost governance”

The second-order effect is organisational. Once the hit rate is visible, every prompt change has a price, and someone has to decide whether a new paragraph at the top of the system prompt is worth $5,000 a day. That decision does not belong to the team that wants the paragraph. It belongs to whoever owns the shared prefix — usually a platform team that does not exist yet, or exists without the mandate. Caching quietly turns prompt editing into a budget decision, and most orgs have no process for making it.

How Hit Rates Decay

No vendor publishes customers' hit rates, so the pattern below is a composite of mechanisms that follow directly from how prefix caching works.[1][3][4] Each one is a reasonable local decision that removes the shared prefix.

The common thread is position. Content is cacheable only up to the first byte that differs between requests. Anything dynamic placed early — a date, a user ID, an experiment flag, a retrieved document — caps the cacheable length at that point, however much static content follows it. Experiments do further damage: with three prompt variants live, each variant warms its own cache, and low-traffic variants may not get a repeat request inside a five-minute lifetime at all.

Rate limits make the decay cost twice. Because cached reads do not count towards Anthropic's input rate limit on most models,[2] a falling hit rate also shrinks your effective throughput. Teams often discover the problem as a sudden wave of 429 errors after a harmless-looking prompt edit — not as a cost spike.

Your Counterargument

“Prompt caching is an implementation detail. Providers are making it automatic, prices keep falling, and an org-level process for prompt edits is bureaucracy that will slow every team down for a line item.”

Automatic caching does remove the work of marking cache breakpoints, and falling prices shrink the absolute numbers. But automation does not change the core constraint: a hit still requires an identical prefix,[3][4] so the hit rate is still set by how prompts are assembled — which is an org decision, not a provider setting. And price cuts tend to raise volume, so the gap between a well-cached and a badly cached deployment rarely shrinks in dollars.

The process needed is light. Nobody has to approve every prompt edit. You need one rule — static content first, dynamic content last — a hit-rate metric on the dashboard, and an owner who gets asked when it drops.

What to Do

  1. Put hit rate on the cost dashboard.

    Report cached-read tokens ÷ total input tokens per endpoint, daily, next to spend. Both major APIs return cached-token counts in usage data.[1][3]

    This week: add the metric for your three most expensive endpoints.

  2. Adopt a prefix layout standard.

    Order every prompt as: stable system instructions → tool definitions → shared reference content → per-user context → the request. Enforce deterministic serialisation of tools and JSON.

    This week: audit one production prompt for dynamic content in its first 1,000 tokens.

  3. Give the shared prefix an owner.

    Changes to the first N tokens go through the platform owner with a projected cost impact. Everything after the prefix stays self-serve for product teams.

    This week: name the owner and write the one-paragraph rule.

  4. Choose cache lifetime from traffic, not habit.

    Five-minute caches suit endpoints with a request every few seconds. Spiky or low-traffic endpoints may only reach break-even with a one-hour cache, despite its 2× write cost.[1]

    This week: list endpoints with fewer than one request per minute per prefix.

In the next 24 hours

Pull yesterday's usage data for your most expensive endpoint and divide cached input tokens by total input tokens. If the result is under 50%, find the first dynamic value in that prompt and move it to the end.
