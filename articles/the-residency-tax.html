The Residency Tax

Legal signed off on keeping EU data in the EU. Nobody priced what that does to capacity, caching and failover.

2026-10-075 min readcompliance-at-scale · data-residency · ai-infrastructure · capacity-planning
Common Assumption

Residency is a configuration flag: pick the EU region, sign the addendum, same system, different location.

Actual Inflection

Each residency boundary is a separate capacity pool that must absorb its own peaks. Splitting one pool into four costs ~26% more reserved capacity under the assumptions here, before cache and failover losses.

Before scale

In February 2025 OpenAI launched data residency in Europe for its API and enterprise products. For API customers, requests made through European projects are handled in-region with zero data retention.[1][2] It was a clear answer to a common procurement blocker for European customers.

Read the implementation details and the architecture appears. European residency is set when a project is created; existing projects cannot be switched to it afterwards.[1][2] On AWS, Bedrock's geographic cross-region inference keeps processing inside a geography such as the US or EU, but prompts and outputs may move between regions inside it, and every destination region has to be allowed by IAM and service control policies.[3] On Azure, provisioned throughput comes in global, data-zone and regional deployment types, and a reservation must match both the deployment type and, for data-zone and regional deployments, the region.[4]

None of these are flags. Each is a boundary — a place where capacity, configuration and keys stop being shared.

Perspective shift — beat 1
“Residency is where the data sits”→“Residency is where the capacity can't move”

Before residency, a global deployment is one pool: when Europe is busy and the US is quiet, capacity flows to where the demand is. A residency commitment cuts that link on purpose. EU traffic can only be served by EU capacity, so the EU pool must be sized for the EU peak alone. The same happens to everything that pools — rate limits, provisioned throughput reservations, prompt caches, fallback routes. Compliance gets a clean answer; capacity planning gets k separate problems.

Partitions Lose the Pooling Discount

Shared capacity is cheap because peaks don't line up. One pool serving four regions needs headroom for the variance of the total, and independent variances add, so the total's standard deviation grows only with the square root of the number of regions. Four separate pools each need their own headroom, so their combined headroom grows with the number of regions itself. This is the same square-root law that sets safety stock in warehouses and staffing in call centres.

Write it down. With k regions, each with mean demand μ and standard deviation σ, and a service level z: a pooled deployment needs kμ + zσ√k; a partitioned one needs kμ + zσk. The gap is zσ(k − √k), and it widens as you add regions and as demand gets spikier — exactly what agentic and batch workloads do to demand.

Real regions are not fully independent, so the true penalty sits somewhere between zero and this bound. But time zones push the other way: regional peaks are offset by hours, and that is the diversity a global pool exploits and a partitioned one gives up.

Compliance gets a clean answer; capacity planning gets k separate problems.

After scale
Perspective shift — beat 2
“We'll fail over to another region”→“Our failover target is now a compliance violation”

The second-order cost shows up in an incident. A global deployment survives a regional outage by sending traffic elsewhere. A residency-bound deployment cannot — or can only within the same geography, which is precisely the boundary that geographic inference profiles enforce.[3] So each partition needs its own failover inside its boundary, which means more headroom, more providers or a documented degraded mode. Teams that promised residency without pricing failover discover the trade-off during their first regional incident, when the only remaining capacity is in a region the contract forbids.

Three Clouds, One Boundary Problem

The major platforms expose residency differently, but each one turns the promise into a boundary that capacity, configuration or keys cannot cross.

The details matter for planning. A project-level setting that cannot be changed after creation[1] means moving an existing workload into residency is a migration — new projects, new keys, new configuration, new usage limits — not a toggle. A reservation that must match a deployment type and region[4] means capacity bought for one boundary cannot be redeployed to another when demand shifts. And a geographic profile that routes within a geography[3] gives you some pooling back, but only inside the boundary, and only if your network and identity policies allow every region it may route to.

Caching fragments along the same lines. A prefix cache is warm only where requests actually land, so a shared system prompt served from four residency boundaries warms four caches, each at a quarter of the traffic. For low-volume regions that can push the hit rate below break-even, which turns an expected discount into a surcharge.

Your Counterargument

“This is over-engineering a legal requirement. Providers handle capacity, standard pay-as-you-go deployments scale automatically, and the square-root maths only matters if you reserve capacity. Pay per token and let the vendor worry about pooling.”

For small and spiky workloads, that is the right call — pay-per-token shifts the pooling problem to the provider, which is a real benefit. It stops working at the scale this site is about. Large workloads buy reserved or provisioned capacity because shared tiers impose rate limits and variable latency, and the moment you reserve, the partition penalty is yours. Even on pay-per-token, per-project and per-region rate limits are still partitions: each boundary gets its own ceiling, and a burst in one region cannot borrow headroom from another.

The fix is not to resist residency. It is to price it before you sign it — and to promise residency per data class and customer tier, not for the whole platform by default.

What to Do

  1. Price every residency commitment before signing.

    For each proposed boundary, compute the extra reserved capacity with the formula above using your real demand variability, and attach the number to the contract review.

    This week: calculate the penalty for your next pending residency request.

  2. Scope residency to data classes, not platforms.

    Many workloads can route de-identified or non-personal requests through a global pool and keep only regulated data in-region. Smaller partitions cost less.

    This week: classify your top five AI workloads by the data they actually send.

  3. Design in-boundary failover now.

    For each residency region, decide in advance between a second in-geography region, a second provider in-region, or a documented degraded mode. Test it.

    This week: write the failover target for each region on one page.

  4. Create residency projects before you need them.

    Where residency is fixed at project creation,[1] provision the in-region projects, keys and limits early, so a customer request does not become a rushed migration.

    This week: list workloads that would need to move if a large EU customer asked tomorrow.

In the next 24 hours

Count the residency boundaries you have already promised, and for each one, write down where its traffic goes during a regional outage. Any answer that crosses the boundary is a contract breach waiting for an incident.
